# plan-session

Generates a structured range session plan and writes it as a `planned`
entry in `/data/sessions.json`.

## When to use

The user asks for a session plan by focus area and (usually) a ball count,
without necessarily having used the `/sessions/plan` page themselves — or
they paste the JSON preview generated by that page and just want it saved.
`golf-session-kickoff` is the conversational front-end to this skill's same
block-generation logic — it gathers context and asks clarifying questions
first, then follows these same steps to persist the plan.

## Steps

1. **Read `CLAUDE.md`** for current focus and schema, and read
   `/data/drills.json` and `/data/progress.json` to find drills and the
   canonical focus area id.
2. **Resolve the focus**: match the user's wording to an existing
   `/data/progress.json` area id where possible (e.g. "sequencing",
   "over the top", "downswing" → `sequencing-over-the-top`). If they name a
   focus with no match, use their wording as free text for `focus` — don't
   force-fit it.
3. **Pick drills**: select drills from `/data/drills.json` whose
   `target_faults` relate to the focus. Prefer 1-2 drills for the "feel
   work" block (simpler/slower drills) and the full relevant set for "drill
   work". If nothing matches well, pick general-purpose drills and say so.
   If `/data/training_plans.json` has a plan with `status: "active"`, let
   the current week's `theme` inform the session's focus/drill choice
   rather than ignoring it.
4. **Build the six blocks** (warm-up, feel work, drill work, transfer,
   pressure test, cool-down), mirroring `lib/data.ts`'s
   `generateSessionPlan`: the first five (warm-up 15%, feel work 15%, drill
   work 35%, transfer 20%, pressure test 10%) are each rounded to the
   nearest 5 balls, and cool-down takes whatever's left over
   (`ballCount - sum of the other five`, floored at 5) so the blocks always
   sum to exactly the ball count requested — don't round cool-down
   independently, or the total will drift from what the user asked for.
   This split follows a blocked-practice → transfer → pressure-test
   progression (see the comment on `generateSessionPlan`), not an arbitrary
   ratio. Below roughly 40 balls the six blocks get short enough to feel
   like busywork rather than real structure — say so to the user and offer
   a simpler 3-block version (warm-up, drill work, transfer) instead of
   handing back six 5-ball blocks as if that were a normal session.
   Each block needs `club`, `balls`, `drills` (ids, empty array where not
   drill-specific), and a one-line `focus_note`.
5. **Write the session** to `/data/sessions.json` with a new id
   `s-YYYY-MM-DD` (today's date, or the date the user specifies), `status:
   "planned"`, empty `post_session_note` (all fields blank/null), and empty
   `stats_ids`. If a session with that exact id already exists (e.g. a
   second session planned the same day), suffix the id (`-b`, `-c`, ...)
   rather than overwriting the earlier one.
6. **Validate** the file is well-formed JSON matching the schema in
   `CLAUDE.md`.
7. **Commit and push**, e.g. `Plan session: <focus>, <date>`. Routine plans
   don't need confirmation first.
8. **Reply to the user** with the block-by-block plan in plain text (not
   just "done") so they can act on it immediately.
